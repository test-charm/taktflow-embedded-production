## 被测功能

**CVC RTE 任务调度的真端到端行为（生成任务体骨架为背景）**

`firmware/ecu/cvc/cfg/Rte_TaskBodies_Cvc.c` 由 `tools/arxmlgen` 从
`gateway/taktflow_vehicle.dbc`（→ `TaktflowSystem.arxml` → `project.yaml`）生成，
文件头为 `GENERATED BY arxmlgen v1.0.0 -- DO NOT EDIT`。它定义六个 OSEK 任务体，
按 **S-OS-11**（优先级降序、同优先级按可运行实体表索引）分派 runnable 并复刻
`Rte_DispatchRunnables`（Rte.c:40-105）的 WdgM checkpoint 语义：

| 任务体 | 分派的 runnable | WdgM checkpoint（seId） |
|---|---|---|
| `Os_Task_Cvc_1ms` | `Can_MainFunction_Read` → `Can_MainFunction_Write` | 无 |
| `Os_Task_Cvc_10ms` | `Com_MainFunction_Rx` → `Swc_EStop` → `Swc_Pedal` → `Swc_VehicleState` → `Swc_Dashboard` → `Com_MainFunction_Tx` → `Can_MainFunction_BusOff` | 2、0、1、4 |
| `Os_Task_Cvc_50ms` | `Swc_Heartbeat_MainFunction` | 3 |
| `Os_Task_Cvc_100ms` / `5000ms` | 无 | 无 |
| `Os_Task_Cvc_Idle` | 先 `Cvc_Os_StartScheduleTables()`，再死循环 `Os_TaskMap_RunMappedFunctions(OS_TASK_CVC_IDLE)` | 无 |

本测试以**真端到端**方式验证任务调度在真实系统上的**可观测后果**（不再用 mock
驱动任务体骨架）：被测系统为**插桩的真实 CVC SIL ECU**（`LLVM_COV=1` 构建），
通过 `/api/test/bsw/rtetaskbodies/cvc` 断言 vcan0 上的真实行为：

- **cadence**：10ms 任务的 `Com_MainFunction_Tx` 让 Vehicle_State / Torque_Request
  以与 DBC GenMsgCycleTime 兼容的 cadence 真实上总线，50ms 任务驱动 CVC_Heartbeat
  ——周期错误的分派顺序/节拍必然导致帧 cadence 断言失败；
- **ftti**：经 UDP DIO（SPI_PEDAL_UDP_PORT=9100，与 SIL-003 同一侧信道）注入
  E-Stop → 10ms 任务链在 FTTI 预算内让 0x001 EStop_Broadcast(Active=1) 到达
  总线，并校验锁存广播流的 DLC=4 / E2E dataId=1 / alive 单调 / CRC；结束时默认
  重启 CVC 容器以清除断电级 E-Stop 永锁。

覆盖链路（全真实，无 mock）：

```text
当POST /api/test/bsw/rtetaskbodies/cvc {op: cadence | op: ftti}
  →（cadence）观测 vcan0 周期帧
  →（ftti）UDP 0xE500 → [IoHwAb → Swc_EStop → 10ms 任务 → Com → PduR → CanIf
    → Can_Posix → vcan0 首帧计时]
  → 断言 results[0].state：found/cycleMs/cycleOk/crcValid；estopFrameSeen/
    withinBudget/frame{...}
```

> 关于生成骨架的覆盖：POSIX SIL 走 legacy 主循环（`Rte_MainFunction` 直接分派），
> **不执行 OSEK 任务体** `Rte_TaskBodies_Cvc.c`；该文件的行级结构覆盖由 OSEK
> 目标/单元层负责（见「覆盖率报告实测」）。
## 被测代码流程图

### 总线观测（cadence / ftti，当前 feature 路径）

```text
[cadence] → [gateway 打开 vcan0] → 对每个 target 收集真实帧
          → [任务体 → Com_MainFunction_Tx → PduR → CanIf → Can_Posix → vcan0]（真实）

```

### 生成任务体骨架（`Rte_TaskBodies_Cvc.c`，代码结构参考）

> 该文件在 POSIX SIL 中**不执行**（legacy 主循环直接分派）；以下流程图为
> 生成代码的结构参考（OS 任务体在 OSEK 目标/单元层执行与覆盖）。


### Os_Task_Cvc_10ms（L68-84）

```text
[10ms] ══→ [Os_TaskMap_RunMappedFunctions(OS_TASK_CVC_10MS)]
```

### Os_Task_Cvc_Idle（L135-142）

```text
[Idle] ══→ [Cvc_Os_StartScheduleTables()]
```

## 代码路径覆盖

本测试被测系统是**真实 ECU 二进制**，覆盖口径为「cadence/ftti 执行期间真实 CVC
运行代码的行覆盖」（插桩 ECU 周期 flush `.profraw` → 网关 `_collect_ecu_coverage_info`
合并，对 BSW 不 ignore）。真实执行覆盖：

- 10ms/50ms 时序链路的真实运行时代码：`Com.c`（周期 TX）、`E2E.c`/`E2E_Sm.c`
  （保护/校验）、`PduR`/`CanIf`/`Can_Posix`（收发）、`Rte.c`（分派）、
  `Swc_EStop.c`（ftti 触发路径）、`IoHwAb_Posix.c`（DIO 注入）等在总线测试中
  出现逐行覆盖。
- 生成配置骨架 `Rte_TaskBodies_Cvc.c`：POSIX SIL 走 legacy 主循环
  （`Rte_MainFunction` 直接分派），**OS OSEK 任务体在 posix 镜像中不执行**，因此
  该文件在 e2e 报告中仅少量命中（实测 6/41 行）。其结构覆盖由 OSEK 目标 /
  单元层负责，属真实执行事实（不为凑数事后驱动）。

| 层次 | 报告中的覆盖来源 | 口径 |
|---|---|---|
| 真实运行时（Com/E2E/PduR/CanIf/MCAL/RTE/SWC） | cadence/ftti 执行期间真实 CVC 的 .profraw | 逐行/函数/区域覆盖 |
| `Rte_TaskBodies_Cvc.c`（生成 OSEK 骨架） | —（posix 不执行） | OSEK 目标/单元层 |

## 无法覆盖的代码说明

### 当前真端到端下的执行事实

- **POSIX SIL 不执行 OSEK 任务体骨架**：真实 CVC 走 legacy 主循环
  （`Rte_MainFunction` 直接分派），`Rte_TaskBodies_Cvc.c` 在 posix 镜像中只少量
  命中（实测 6/41 行）——该文件是 OSEK 目标代码，其**逐行结构覆盖由 OSEK 目标
  / 单元层负责**。这是"覆盖=真实执行"口径的如实反映，**不**为凑数而事后驱动。
- **节拍非实时**：真实帧 cadence 约为 DBC 名义的 3x（Docker），`cycleOk` 用
  有界带宽 + 稳定周期性判定。
- **E-Stop 永锁**：注入后 0x001 广播在锁存期间持续；`ftti` 默认重启 CVC 容器
  清锁存并验证恢复。
